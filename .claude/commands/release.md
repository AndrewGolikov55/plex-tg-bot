# /release — подготовить новый релиз

Выполни релиз `plex-tg-bot`: проанализируй коммиты, подними версию (semver), обнови `CHANGELOG.md`, прогони qualifying checks, закоммить и протолкни тег. CD-цепочка дальше: GitHub Actions release.yml собирает multi-arch образ → ghcr.io → Portainer webhook → автодеплой.

В этом проекте **нет рассылки пользователям** — только changelog и тег. Аудитория CHANGELOG — оператор форка и его будущий self.

## Контекст

- Версия хранится в **двух** местах и они **должны совпадать**:
  - `pyproject.toml` → `[project].version`
  - `src/plex_tg_bot/__init__.py` → `__version__`
- Технический журнал: `CHANGELOG.md` (формат Keep a Changelog).
- Релиз триггерится `git push --follow-tags` с тегом `vX.Y.Z`. Дальше всё автоматически (release.yml → ghcr.io → Portainer webhook).
- Коммиты подписывать **не нужно**: используй `git commit --no-gpg-sign -m "..."` и `git tag --no-sign`.
- Quality checks: `uv run ruff check .`, `uv run mypy`, `uv run pytest -q`. Все три должны быть зелёными перед commit'ом.

## Последовательность действий

### 1. Убедись в чистом состоянии

```bash
git status
git rev-parse --abbrev-ref HEAD
git pull --ff-only
```

- Должен быть `main`, без uncommitted/untracked файлов, связанных с релизом.
- Если user на другой ветке — спроси, действительно ли релизим отсюда.

### 2. Определи стартовую точку

```bash
git describe --tags --abbrev=0
```

- Это предыдущий тег. Если тегов нет — работай от начала истории.
- Прочитай текущую версию из `pyproject.toml` (`[project].version`).

### 3. Собери коммиты для анализа

```bash
git log <prev_tag>..HEAD --pretty=format:"%H%x00%s%x00%b%x1e" --no-merges
```

Для каждого коммита посмотри ещё и diff, чтобы классифицировать по реальным изменениям, а не только по commit message:

```bash
git show --stat <hash>
```

Если diff маленький — `git show <hash>`. Если большой — открой через Read только изменённые файлы.

### 4. Классифицируй каждый коммит

Присвой каждому коммиту одну категорию:

| Категория | Попадает в CHANGELOG раздел | Что относится |
|-----------|----------------------------|---------------|
| `feat` | **Added** | новая команда бота, новая кнопка/меню, новый параметр конфигурации, новая фича в админ-панели, новая локаль |
| `fix` | **Fixed** | исправление бага, который видел юзер бота ИЛИ оператор: упавший хендлер, неработающая кнопка, неправильный текст, ошибка в Plex/Overseerr API клиенте |
| `improvement` | **Changed** | изменение поведения существующей фичи, UX-правки, изменение текстов локалей, изменение дефолтов, breaking change в env-переменной |
| `internal` | **Internal** | рефакторинг, типизация, lint/mypy/pytest правки, CI workflow, миграции схемы БД без видимого эффекта, обновление зависимостей, чистка мёртвого кода, доки |

**Ключевой вопрос при классификации**: «Заметит ли это оператор форка, читающий CHANGELOG перед обновлением?». Если нет (косметика, refactor) — `internal`. CHANGELOG этого проекта пишется и для оператора-self в будущем — туда идут ВСЕ категории.

Граничные случаи:
- Новый env var с дефолтом → `feat` (Added).
- Удалённый/переименованный env var → `improvement` (Changed) с пометкой **BREAKING** в начале строки.
- Изменение значения локалей (текст кнопок, ответы пользователю) → `improvement`.
- Тесты на новый код → ходят вместе с feat-коммитом, отдельно в Internal не попадают.
- Тесты, которые что-то новое валидируют (contract tests, fuzz) → `internal` или `feat` если фича обнаружена.

### 5. Определи следующую версию (semver)

- Если есть хотя бы один коммит с `BREAKING CHANGE:` в теле, префиксом `feat!:`/`fix!:`, или удалённым/переименованным public env var → **major** (0.2.0 → 1.0.0).
- Иначе если есть хотя бы один `feat` → **minor** (0.1.0 → 0.2.0).
- Иначе если есть `fix`/`improvement` → **patch** (0.1.0 → 0.1.1).
- Если все коммиты `internal` → **patch**.

### 6. Обнови версию в обоих местах

- `pyproject.toml`: `[project].version = "X.Y.Z"`.
- `src/plex_tg_bot/__init__.py`: `__version__ = "X.Y.Z"`.

Они **должны** совпадать. test_smoke использует regex (не сравнивает с константой), поэтому тест не упадёт сам по себе — следи внимательно глазами.

### 7. Обнови `CHANGELOG.md`

Добавь новую секцию **над** предыдущими версиями. Формат:

```markdown
## [X.Y.Z] - YYYY-MM-DD

### Added
- описание нового функционала

### Changed
- описание изменений

### Fixed
- описание исправлений

### Internal
- краткий список технических правок
```

- Пропускай пустые подсекции.
- Пиши короткими императивными фразами на английском (это OSS-проект, английский — primary): «Add `/admin sync` button», «Fix `/start` crash when user has no username».
- `Internal` можно собрать в один пункт: «Refactor admin module, bump aiogram, drop unused i18n keys».
- Если в релизе есть breaking change — первой строкой раздела `### Changed` напиши `**BREAKING:** ...`.
- Используй сегодняшнюю дату (`date +%Y-%m-%d`).

### 8. Прогони проверки качества

**Обязательный шаг перед commit'ом.** Запусти все три:

```bash
uv run ruff check .
uv run mypy
uv run pytest -q
```

- **Если любая проверка упала** — не коммить. Сначала почини:
  - `ruff` → применяй `uv run ruff check --fix .` если ошибки автоматически исправимы, иначе правь руками.
  - `mypy` → исправляй типы, добавляй аннотации; не глуши `# type: ignore` без необходимости.
  - `pytest` → смотри упавшие тесты, чини код или тест (если тест реально неверный).
- После исправления **перезапусти все три**. Релиз не уходит пока все три не будут зелёными.
- Если ошибка в коде, который внесла не текущая сессия, а был в `main` до неё — сообщи об этом пользователю и спроси, чинить ли здесь или релизить как есть.

### 9. Покажи результат пользователю

Выведи в чат:
- Предыдущая и новая версия.
- Список коммитов с классификацией (категория | hash | one-line subject).
- Добавленный блок CHANGELOG.
- Результаты quality checks (зелёные).

Жди подтверждения. **Не коммить и не пушь сам до одобрения.** Если пользователь попросит правки — применяй и снова покажи.

### 10. После подтверждения — коммит и пуш

```bash
git add pyproject.toml src/plex_tg_bot/__init__.py CHANGELOG.md
git commit --no-gpg-sign -m "chore(release): vX.Y.Z"
git tag -a vX.Y.Z -m "vX.Y.Z" --no-sign
git push origin main --follow-tags
```

- Автор коммита — глобальные настройки git (никаких `Co-Authored-By: Claude`).
- Если в процессе сессии были другие коммиты (например, fixes по результатам review перед релизом) — оставь их под их собственным авторством с conventional-формат сообщениями.

### 11. Подожди CD-цепочку и сообщи

После push'а тега:

```bash
gh run list --workflow Release --limit 1 --json databaseId,status,conclusion
```

Подожди завершения (через `gh run watch <id>` или polling). Должны пройти оба job'а:
- `build-push` — собирает и пушит multi-arch образ в `ghcr.io/<owner>/plex-tg-bot:vX.Y.Z` + `:latest`.
- `redeploy` — POST на Portainer webhook (URL в secret `PORTAINER_WEBHOOK`); если secret не задан — шаг просто скипается без падения.

Когда release workflow зелёный — релиз состоялся. Сообщи пользователю:
- Новый тег.
- Ссылку на release run в Actions (получишь из `gh run view <id> --json url`).
- Список ghcr.io тегов нового образа.
- Будет ли auto-redeploy в Portainer (да, если PORTAINER_WEBHOOK задан в secrets; нет — если шаг скипнулся).

## Не делай

- **Не делай `git push --force`** на main или на тег.
- **Не указывай себя соавтором** в коммитах (`Co-Authored-By: Claude`).
- **Не коммить, если quality checks красные.**
- **Не релизи если git status показывает untracked файлы с подозрительными именами** (`.env.prod`, `dump.sql`, `*.pem`) — спроси что это.
- **Не используй `git tag` без `-a` (lightweight)** — релизные теги должны быть annotated.
- **Не правь `__version__` или `pyproject.toml` отдельно** — они идут вместе.
- **Не забывай про CHANGELOG** — даже если все коммиты Internal, секция должна появиться. CD не требует её, но оператор-self потом не вспомнит, что в этом релизе.
